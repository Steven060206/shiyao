## 1. 使用流程

### 1.1 第一次打开

1. 显示简短引导，依次检查本机 NapCat 是否可用、QQ 是否已登录及接收连接是否就绪；缺少 NapCat 时提供安装与配置指引，未登录时提示用户在 NapCat 对应的 QQ 环境完成登录。连接就绪前说明当前没有接收 QQ 新消息。
2. 尝试读取最近 7 天群消息，展示每个群的读取状态及失败原因，软件仍可正常操作；历史导入中的事项逐步显示，读取结果持续刷新列表及对应卡片，不发送历史汇总系统通知。
3. 从群名与消息提出课程、群关联候选，用户确认、修改或排除；不要求先手填课程名单。
   用户提供的截图红框均为学校相关群；群名通常正规但存在非正式名称，名称风格只辅助候选，不能作为排除依据。截断名称须取得真实群列表后核对。
4. 展示两张桌面卡片、临期/逾期高亮及处理入口，说明第一版没有系统弹窗或声音。
5. 完成引导后，默认登录 Windows 自动启动并在托盘后台运行；设置中可关闭自动启动。

连接和历史读取失败时保留已经保存的任务，提供重试或返回设置的入口；引导进度保存在本机，可以继续完成。

引导记录当前 QQ 账号，展示账号与群列表供用户核对；课程候选和可信发布者候选可在使用中确认，不要求第一次打开就手填完整课程或老师名单。本应用自启动仅代表应用已运行，NapCat 与 QQ 的就绪状态仍按第 6 节独立检查。

### 1.2 日常查看

- 主界面左侧为任务、待确认、通知、已完成、设置；右侧保持事项列表和详情栏。
- 从桌面或托盘正常打开时，有待确认事项则进入待确认，否则进入任务。
- 点击桌面卡片的详情或待确认事项时，打开主界面对应事项原文、图片与变更记录。
- 标题搜索配合课程、来源群及状态筛选；新任务、通知和待确认显示未读数量与小红点。
- 只有实际打开事项详情才标记已读；打开整个列表不清空所有未读。
- 已读与已处理分开：看过待确认事项后仍保留在待确认列表和桌面卡片，直到确认或忽略。
- 已读事项收到明确延期、取消、执行要求变化或新的行动要求时，按重要变更版本重新标为未读，显示“已延期”“已取消”或“有新要求”等标记；重复证据、消息重放和纯补充说明不反复制造未读。查看详情时记录实际呈现的版本，随后到达的新变更仍保持未读。
- 待确认列表按具体原因筛选，包括时间缺失、时间类型不明、课程/对象不明、来源不确定、疑似重复和与手动信息冲突；每项显示原文、疑点与对应处理入口，不只提供笼统的“确认”按钮。

### 1.3 新增、修改和证据

- 自动提取任务和手动新增任务使用同一套优先级、提醒及完成规则；手动新增显示来源“手动添加”。
- 用户可编辑标题、课程、提交截止或考试/活动开始日期及具体时刻和优先级。手动修改按字段保存，不因重复读取同一消息而恢复旧值；后续明确变更与手动确认值冲突时，保留正式值并展示待确认差异，按第 7.3 节处理。
- 需要行动但缺少可靠时间的事项进入待确认；补齐并确认时间类型及信息后进入正式任务卡片，按有效截止/开始排序和高亮。
- 普通通知可手动加入任务；缺少必要时间时先补齐确认。
- 详情保留原消息、发送时间、来源、图片和各次明确变更，用户可以核对任务为什么被修改。
- 图片显示缩略图，点击放大；OCR 文字默认折叠。
- 图片日期显示为建议，用户可修改、确认或拒绝。确认只作用于该项建议，OCR 不自动覆盖文字或用户已确认的正式时间。
- 一条消息中的独立行动可拆成多项任务，各自拥有时间、状态与提醒，详情共同引用原消息；同一事项在不同群的明确重复发布可以合并证据。详情提供“合并重复事项”和“拆开错误合并”入口，变更前展示涉及事项及时间、状态差异，规则见第 7.2 节。

### 1.3.1 待确认如何处理

| 原因 | 用户看到的内容 | 处理方式 |
| --- | --- | --- |
| 缺少时间或时间类型不明 | 行动原文与缺失字段 | 补充日期/时刻，选择提交截止或开始时间；取消进入正式任务的操作时保留候选 |
| 课程或本人相关性不明 | 来源群、对象限定与课程候选 | 选择课程、确认与本人相关，或忽略；已有确认关系可复用 |
| 来源或变更含义不确定 | 发布者、引用上下文与疑问/转述语句 | 核对证据后接受或拒绝变更，必要时确认该群的可信发布者 |
| 疑似重复或合并冲突 | 候选事项及时间、完成状态差异 | 合并、保持独立，或拆开既有错误合并 |
| 与手动确认值冲突 | 当前正式值、手动来源与新建议并列 | 接受新值或保留现值；只处理涉及字段 |

与已有正式事项关联的待确认变更单独保存为建议，待确认列表链接到原事项，不创建第二条正式任务。确认必须同时满足所需字段、本人相关性与关联条件；拒绝某项建议保留原正式状态和证据。重复收到已拒绝的同一建议不重新入队；新的实质证据可形成新的待确认建议。

### 1.4 完成、忽略与归档

- 点击完成立即移入已完成记录并停止任务提醒，不弹二次确认框。
- 即时提示、已完成记录和详情中的按钮统一写“撤销”；完成后 1 小时内可撤销。
- 忽略待确认事项后从待确认列表移出；即时提示和待确认页的“最近忽略”区域提供“撤销”，期限为操作后 24 小时。
- 重启后入口仍可找到，期限从原操作时刻计算，不重新开始倒计时。
- 撤销仅撤销该次用户操作影响的处理状态，使用最新有效时间、要求和证据刷新卡片；不恢复旧的整份事项快照。
- 到期仅结束撤销机会，完成记录、忽略记录及相关证据继续保留。
- 任务详情提供“归档”入口，归档后标记为已归档、移出待办及桌面卡片、不记为已完成，不删除证据。任务页提供“已归档”状态筛选，详情可查看原要求和归档记录，并由用户手动恢复待办。
- 归档记录不因重启、重读或普通补充自动恢复；归档后收到明确新行动要求时形成关联待确认建议，用户接受后再恢复待办，避免自动覆盖用户的归档决定。手动恢复后使用最新有效信息刷新卡片。
- 老师明确取消且满足第 7.1 节的来源与关联条件时，停止该任务后续时间提醒，移出待办和桌面卡片，保留“已取消”记录及原始消息；不记为用户已完成。取消变更保留在主界面记录中，不发系统通知；记录可从任务页的“已取消”状态筛选查看。
- 已完成任务收到满足第 7.1 节来源条件、能明确关联的新行动要求时，自动恢复为待办，在卡片及主界面标出新要求；保留此前完成记录及新旧消息证据。普通补充说明不自动恢复；关联或必要正式时间信息无法确定时，仍按既有规则进入待确认。
- 撤销前检查后续变更：完成后明确取消的事项继续保持已取消，旧完成操作显示“已被后续取消替代，无法撤销”；完成后仅明确延期且无字段冲突时，撤销恢复待办并采用最新时间。已因新行动要求恢复待办时，旧完成操作不再次恢复或重发提醒。忽略后已接受新建议的事项，也不能被旧忽略操作重新改回待确认；完整顺序见第 7.3 节。

### 1.5 桌面卡片、主题和设置

- 提醒事项和待确认两张独立桌面卡片首次左右排列，保留现有原型的布局、配色和动效；各自可拖动和调整大小。
- 组件首次根据屏幕可用区域自动摆放，避开任务栏并保持可见；记住用户拖动和调整大小后的布局。
- 待确认处理完后隐藏其卡片；提醒事项清空后显示“暂无待办”。
- 卡片仅在桌面显示，不覆盖其他软件；点击详情打开主界面并定位该事项。
- 提醒事项按优先级与有效时间排序：提交任务使用截止时间，考试/需要参加的活动使用开始时间；临期、逾期或开始时间已过分别标记。普通通知只在主界面通知列表展示。
- 主题提供跟随系统、浅色、深色；默认跟随 Windows，主界面与桌面卡片同步主题选择。主界面深色使用纯黑，桌面卡片按2026-10-13外观反馈使用柔和半透明圆角材质，无待办时缩短可见面板，不覆盖原布局偏好。
- 颜色过渡沿用原型的 320ms；按钮按压和卡片悬停动效尊重减少动画设置。
- 2026-10-13新增：标题拖动靠近另一张卡片自动吸附，左右只对齐顶部并保留各自高度（用户选择A），上下按可见高度衔接并对齐左边；拖离解除，松手保存原布局格式。设置提供底色透明度0%～100%，文字保持清晰，重开及备份恢复保留。
- 关闭主窗口默认隐藏到托盘，设置可改成退出；托盘始终提供明确的退出入口。
- 设置包含自动启动、关闭行为、主题、动画、连接、课程/机器人/可信发布者确认管理，以及本地备份和恢复。
- 系统提醒、自定义时间提醒和安静时段入口随通知渠道取消；手机版尚未确定开发。

## 2. 桌面提示

### 2.1 时间类型和到期行为

| 时间类型 | 保存和卡片依据 | 时间过去后 |
| --- | --- | --- |
| 提交截止 | 保存截止日期，原文可靠时再保存时刻 | 显示逾期和高亮，保留待办，不自动完成 |
| 考试或需参加的活动开始 | 单独保存开始日期/时刻及时间类型 | 显示“开始时间已过”，不当成作业逾期，不自动认定参加或完成 |
| 报名截止与活动开始同时出现 | 报名行动和活动信息分别保存并关联 | 各按自己的时间处理，完成报名不自动完成参加活动 |
| 仅背景日期或与本人无关的日期 | 保留消息证据 | 不生成正式任务时间 |

只有日期时，日期当天仍有效，次日才显示逾期或日期已过；不填零点、23:59 或虚构的考试时刻。图片日期仍须用户确认。相对日期按原发送时间和时区解释。

### 2.2 卡片状态

- 本地 P0～P3、有效截止/开始排序、临期和逾期高亮继续有效；实时、手动、历史、补漏及修复的新事项统一刷新卡片。
- 待确认卡片在有未处理项时常驻，全部处理完隐藏；提醒事项清空显示“暂无待办”。普通群通知只保存在 App 通知列表，不增加第三张卡片。
- 有效延期按字段保护接受后重新排序及高亮；无法确认的冲突保留正式值并进入待确认。明确取消移出卡片，保留“已取消”记录，不记为完成。
- 主界面保留原文、图片、处理及变更记录和 QQ 连接状态；点击卡片详情定位当前事项，完成操作核对账号/事项版本。
- 重启、睡眠恢复和重连后读取当前工作区并刷新卡片，不补发系统通知。

### 2.3 已取消渠道与历史产物

2026-10-12 用户选择 A，取消全部 Windows 系统通知弹窗和声音：24/2 小时时间节点、日期前日 12:00、自定义提醒、新发现/变更通知、恢复/历史/迟到/修复汇总、断线超过 5 分钟通知、通知点击路由和权限恢复均移出当前范围。系统提醒、自定义时间提醒、测试通知和安静时段界面入口一并取消。

旧 ReminderPlanner、SQLite plans/ledger、提醒设置和通知 probe 验证作为历史产物保留，不删除原消息、事项、证据或用户数据，不再作为后续 Windows 接入工作。历史持久化批次、去重和消息顺序仍服务于接收/分析，但不再带通知汇总时限或发送要求。

## 3. 断线和使用中失败

- 界面分别显示 NapCat 可用性、QQ 登录状态、消息接收连接和历史补漏状态；连接断开后后台自动尝试恢复，不能用单一“已连接”标签代表这些状态均正常。
- 主界面及桌面卡片显示持续断线状态和原因，后台自动重连；不发送持续断开超过 5 分钟的系统通知。
- NapCat 断线不影响本地已有任务的查看、完成和提醒；恢复后尝试逐群补漏。
- 历史读取不足或失败显示群和原因，不显示虚假的“已补全 7 天”。
- OCR 失败保留原图，展示识别失败及重试入口，用户仍可手动补齐。
- 保存操作必须收到后端成功确认后才显示成功；失败保留编辑内容，允许重试。
- 正常退出后停止接收和工作区刷新；下次运行恢复未完成处理并刷新卡片。
- 检测到 QQ 退出或账号变更时暂停该连接的接收归档与规则处理，显示原因；当前账号的本地任务仍可查看和提醒。账号切换须按第 6 节显式确认，不能把新账号的消息写进旧账号的数据空间。
- 桌面附着异常、图片证据缺失和备份/恢复失败分别显示可处理原因；不能清空已有任务绕过错误。

## 4. 应用结构和运行边界

开发者选定方案：

| 组件 | 职责 |
| --- | --- |
| C# WPF 主进程 | 应用生命周期、单实例、托盘、窗口、设置、接收、规则处理、数据库和提醒 |
| WebView2 主界面 | 复用 HTML/CSS/JS 布局，显示列表、详情、引导和设置 |
| WPF 桌面宿主窗口 | 承载桌面组件的本地界面，处理真实窗口层级、移动、缩放及显示器变化 |
| 独立 OCR 工作进程 | 使用 RapidOCR 和随包模型识别本地图片，返回文字、位置与置信度 |
| SQLite 与证据目录 | 保存正式状态、消息证据、图片、同步位置、提醒记录及撤销期限 |

采用 .NET 10 LTS、Windows x64 作为开发和发布基线。先在本机 Windows 11 64 位验证；其他 Windows 版本须另行实际验证，不能根据框架支持范围直接宣布桌面卡片可用。

不增加云端 AI 或消息上传服务。NapCat 与 OCR 均在本机运行，数据库是任务状态的唯一正式来源，前端不以浏览器本地存储保存正式任务。

第二次启动或卡片打开请求交给已有主进程，避免启动两套接收和工作区服务。关闭主界面不关闭后台服务；明确退出才停止后台服务。

## 5. 本地数据设计

### 5.1 保存哪些信息

| 数据 | 必要内容和约束 |
| --- | --- |
| 账号数据空间 | 当前 QQ 账号、账号对应的数据目录、启用状态；同一时刻只有当前账号显示桌面卡片 |
| 原始消息 | 所属 QQ 账号、群 ID、消息 ID、发送账号、原始发送时刻、文本和消息段、实时/历史来源及批次；账号 + 群 ID + 消息 ID 唯一 |
| 事项 | 所属账号、稳定事项 ID、标题、课程/来源、任务/通知类别、确认状态、待办/已完成/已取消/已归档处理状态、归档记录、优先级及逐字段手动覆盖、正式时间、重要变更版本与已查看版本；待确认列表由确认状态及关联建议生成 |
| 时间信息与来源 | 时间类型、日期、可选时刻、可选结束时间、解释时区、文字/经确认图片/用户来源及字段版本；日期精度与时刻精度分别记录 |
| 事项证据 | 事项与原消息/图片/OCR 的多对多关联；一条消息可支持多项任务，一项任务可引用多个群的证据，合并或拆分后不丢失原证据 |
| 课程与群关联 | 自动候选和用户确认结果分开保存，支持修改与排除；关联版本、受影响群、重查批次及结果范围 |
| 机器人排除 | 经用户确认的账号记录，支持撤销；候选账号不自动排除 |
| 可信发布者 | 所属账号与群、发布者 ID、用户确认依据及撤销状态；群昵称或职位文字不等于已确认可信身份 |
| 待确认建议 | 对应正式事项或新候选、疑点代码、缺失字段、旧正式值与建议值、证据、建议指纹及接受/拒绝状态 |
| 变更记录 | 原值、新值、关联证据、事项版本、有效原消息顺序、变更类型、重要变更版本及已查看版本 |
| 旧提醒记录（历史保留） | 既有 plans/ledger、版本、节点、投递标识及状态保留，不新增 Windows 调度或投递 |
| 合并与拆分记录 | 保留事项 ID、旧 ID 跳转关系、成员及字段/状态选择、拆分去向、原操作与证据；已发送节点历史不可抹除 |
| 同步与处理进度 | 各群读取位置、历史状态、处理批次、已处理消息/规则版本、汇总状态、OCR 待处理任务及失败原因 |
| 操作与设置 | 操作 ID、完成/忽略时刻、撤销期限、影响字段及依赖版本、后续替代关系、主题、自启动、关闭行为、卡片布局、引导进度和备份记录 |

只有日期的截止或开始信息保存为日期，不填入零点或 23:59 作为正式时刻。相对日期按原消息发送时刻的日历上下文解释。群和消息标识跨前端传递时使用字符串，避免 JavaScript 大整数精度丢失。

数据库修改、消息处理进度和证据关联通过事务提交。重复消息命中既有记录，更新处理结果而非创建第二个事项。

事项版本、正式时间版本和重要变更未读版本分别管理，既有提醒计划版本及历史台账保留。待确认建议与正式值分开，接受建议、记录证据和更新正式字段在同一事务内完成，再读取快照刷新卡片。所有编辑和撤销均携带操作 ID 及依赖版本，后端发现并发变化时重新检查适用性，不能用旧表单覆盖新变更。

### 5.2 数据目录和保留

- 默认使用 Windows 当前用户的本地应用数据目录；安装目录与数据目录分开。
- 已成事项的原消息、原图、完成/忽略/归档记录长期保留，分析窗口不限制其寿命。
- 未关联任何事项的临时消息和图片缓存只用于最近 7 天分析；清理前检查没有证据关联或待处理操作。
- 日志滚动保存最近 14 天，记录模块、时间、错误摘要和必要标识，不记录 Token、QQ 登录凭据或整段聊天正文。
- NapCat Token 使用 Windows 当前用户保护机制保存，设置中不回显原值；不会写入项目文档。
- 数据结构升级前先生成数据库与关联证据的完整本地备份，通过事务迁移；失败时保留原数据并报告，禁止用重建空库覆盖已有数据。备份与恢复流程见下一节。

### 5.3 本地备份和恢复

- 设置提供“导出备份”和“恢复备份”。备份是当前账号的数据快照，包含数据库、被快照引用的原图及其他证据文件、课程/群/可信发布者关系、手动覆盖、提醒发送记录、撤销期限、设置和版本清单；不能只备份任务标题或数据库而漏掉图片。
- 使用 SQLite Backup API 生成一致数据库快照，再按该快照的证据清单复制文件；备份期间禁止清理被引用证据，新增证据先完整落盘再建立数据库关联。不得直接复制正在写入的单个数据库文件来冒充完整快照。
- 清单记录备份格式、数据结构版本、应用/规则版本、账号、生成时刻、证据相对路径及文件校验值。写到临时位置，校验通过后才成为可恢复的完整备份；缺少必要图片或空间不足时保留原数据，明确报告不完整或失败。
- 备份不包含 NapCat Token、QQ 登录凭据或其他账号登录材料。恢复后提示重新核对连接设置；跨电脑恢复也不尝试复用原 Windows 用户保护的凭据。备份内的聊天和图片由用户自行保存在本地。
- 恢复前先展示备份账号、时刻及将恢复的内容，并要求用户确认覆盖当前账号数据；自动生成当前数据的恢复前备份。第一版采用整份恢复，不实现两个历史备份的自动混合。
- 暂停相关账号的接收处理与卡片操作，在独立目录校验数据库完整性、版本兼容性、账号及必要证据，再整体切换数据。失败时保持原目录可用；成功后重新连接并按同步位置尽力补漏。切换期间收到但尚未处理的消息在当前账号验证后继续处理。
- 旧提醒台账和撤销期限保持原值，恢复不重置撤销时限；恢复后刷新当前任务和卡片，不发送旧节点或恢复汇总系统通知。
- 升级前自动备份和恢复前自动备份采用同一完整格式；界面可查看备份结果并打开本地位置。真实验收须包含跨目录/跨电脑恢复、图片可查看和损坏备份失败后的原数据保留。

## 6. NapCat 接入和补漏

### 6.1 依赖就绪与账号绑定

- 本应用安装包包含自身运行依赖与 OCR，不默认视为已经安装、启动或登录 NapCat。首次引导先检测本机服务并提供安装、OneBot 正向 WebSocket 与 Token 配置步骤；NapCat/QQ 未就绪不阻止用户查看已有本地任务。
- 第一版由用户安装和启动 NapCat、完成对应 QQ 登录，本应用连接已经配置的本机接口；不嵌入 NapCat 安装器，不代填 QQ 密码。连接成功后核对登录号信息与可用接口，再读取群列表。
- NapCat 提供 Shell 和 Framework 两种接入模式。Shell 是无界面接管路线；同一账号不能同时登录普通 QQ 和 Shell，不能把两个进程同时作为同一账号的接收端，也不能把 Shell 记作可聊天桌面 QQ。Framework 在桌面 QQ 进程中加载 NapCat；本机 QQ `9.9.36-53644` 已实际加载并自动登录，只读接口通过，用户确认聊天列表和窗口正常显示。实时群事件限定范围通过（观察到 1 条），长期稳定性尚未验证，见 [集成探针记录](../../verification/integration-probes.md)。本应用不强制关闭用户当前 QQ，也不把双开同账号当作可用方案。
- 状态分别展示“NapCat 不可用”“QQ 未登录/状态未知”“接收连接中/已就绪”“历史读取中/部分失败/本批读取结束”。传输连接或心跳存在不能单独证明 QQ 正常；没有新消息也不能直接断定掉线。状态接口不可用时显示未知并给出检查指引。
- Windows 登录自动启动只启动本应用，恢复本地事项和卡片，不接管 QQ。用户点击软件入口或“自动同步”时才切换 QQ；依赖失败显示原因并保留原数据，不发送系统通知。
- 收到的消息账号标识必须与当前绑定 QQ 一致。发现其他账号时暂停该连接消息的处理，提示用户核对或切换，不能自动覆盖绑定关系。
- 用户显式确认切换账号后，使用该账号独立数据库、证据目录、课程关系和读取位置，停止原账号的卡片操作；只有当前账号工作区显示在卡片中。原账号数据保留，切回时刷新当前状态，不把两个账号的已完成状态、机器人名单或提醒历史混用。
- 切换账号后卡片和主界面统一读取新账号工作区，操作核对账号和依赖版本；延迟到达的旧账号卡片操作不查询或修改新账号库。

### 6.2 接收、分页和补漏

- 每次手动打开拾要或点击“自动同步”执行一轮；同一轮内重连补漏，结束后断开接口并恢复普通 QQ。允许自动退出已运行的普通 QQ，先验证依赖与置顶桥再切换；失败、取消和五分钟超时也尝试恢复。取消 08:00/12:00/20:00 定时同步，后台登录自启动只展示本地数据。
- 按游戏进程检测，游戏期间延后同步，中途开始游戏时停止读取并恢复普通 QQ，退出后将多个点击请求合并补一次；切回桌面不代表游戏结束。自动扫描本机游戏并更新检测名单，默认应用启动及每日扫描，游戏期间延后目录扫描；自动发现、缓存与进程检测已接入，本机扫描发现 19 个安装目录。未就绪时暂停同步，扫描失败保留旧名单并重试；不把启动器或所有全屏软件都当成游戏，不宣称未知来源游戏均已识别。
- 使用 OneBot 正向 WebSocket，WPF 作为客户端连接本机 NapCat，避免另开对外服务端口。
- QQ 接入只读，不向 QQ 群或私聊发送消息。学校群通知、测试提醒及任务提醒不通过 QQ 发送；第一版通过两张桌面卡片提示任务和待确认，不发送 Windows 系统通知。
- 使用 echo 对应 API 请求和响应；群消息事件与接口响应分别解析，识别群消息并排除私聊。
- 只读取当前 QQ 中置顶的群聊，实时、首次历史与断线补漏使用同一范围；经用户确认的机器人账号忽略。连接及重连重新读取置顶名单，运行中核对置顶变化，失败暂停读取，不回退到全群；取消置顶不自动删除已有事项或证据。
- 每次手动打开或点击自动同步在非游戏时逐个置顶群、分批尝试回溯最近 7 天；同步批次内恢复连接后，仅在当前仍置顶的群中尝试补漏。点击触发及游戏后补同步复用历史分页与去重，读取结果刷新卡片，不发送批次系统通知；同步之外不持续处理实时消息。
- 群历史通过 get_group_msg_history 的当前接口读取，以实际返回消息定位下一批；不把 message_seq 当成可随意加减的连续序号。
- 分页重叠用群及消息 ID 去重，接收和历史读取的重叠不产生重复任务。
- 每群保存读取结果、进度和失败原因；历史数据缺失不影响其他群继续处理。
- 在线消息先持久化再交给本地处理队列。崩溃或重启后从未完成的处理状态继续。
- WebSocket 重连不代表服务器会重放离线消息，7 天回溯和补漏均为尽力尝试，完整性必须通过真实 QQ 返回验证。
- 历史处理按原消息时间和可核实的群内顺序应用变更；晚到的旧通知不覆盖已经确认的较新要求。跨群转发能取得原始上下文时保留原时刻；无法判断两个冲突通知先后时进入待确认，不能仅按本机到达顺序选最新。
- 锁定并记录真实验证所用的 NapCat、QQ 与接口版本，验证登录状态、消息字段和历史分页；版本变化后重做受影响检查，不把某次接口成功扩大为所有版本保证。

## 7. 本地规则、课程关联和任务合并

### 7.1 提取顺序与自动处理边界

处理顺序：

1. 标准化消息段，保留文字、图片、回复上下文和来源时间。
2. 按已确认账号排除规则处理，提取课程/群候选，不因重复内容擅自排除老师或同学。
3. 综合行动要求、对象限定、课程关系、来源及日期语义，判断是否属于学校通知或任务；区分明确陈述与疑问、猜测、转述、引用旧通知和否定语义，不按单个关键词或字数机械过滤。
4. 基于原发送时间解析相对日期，区分提交截止、考试/活动开始和其他日期；无法可靠区分或存在时间冲突时进入待确认。
5. 判断与本人课程的相关性；关系不明确的进入待确认，自愿活动和竞赛作为通知。
6. 按独立行动与时间要求拆分候选，给事项关联证据并计算自动优先级；手动优先级作为独立覆盖保存。
7. 使用明确的事项名称、群/课程、引用消息和上下文关联已有事项；证据不足时形成待确认，不只因标题相似就覆盖。
8. 满足本节来源与关联条件的明确催交补充到原任务；延期、取消和要求修改形成变更版本并刷新卡片，在主界面保留记录，不发系统通知。明确取消停止后续时间提醒、移出待办及桌面卡片，保留“已取消”记录及证据；已完成任务收到可靠新行动要求及必要时间时恢复待办并标出新要求，保留此前完成记录及新旧证据。普通补充不恢复，来源、关联或必要正式时间信息不确定仍待确认。

基础优先级按本地日历依次匹配：逾期/今天 P0，未来 3 天内 P1，未来 7 天内 P2，更晚 P3。明确的成绩、资格或逾期不收后果可提高一级，检查否定语义；逾期高亮与用户手动优先级分开保存。

OCR 建议和未确认关联不能触发自动任务覆盖。规则版本与处理原因记录在本地，便于用真实误判、漏判例子改进；不引入云端或本地大语言模型。

自动建立正式任务需要同时有清楚的行动、可确认的本人/课程相关性和有效时间类型及信息。对日期、对象或关联任一关键条件不能确定时，形成待确认而不是静默丢弃；普通聊天和明确无关消息仍可排除，并保留可用于排查的处理原因。

自动取消、覆盖已有时间或恢复已完成任务属于高影响变更：必须能明确关联目标事项、识别有效新要求，并具备用户确认过的发布者身份或已确认原通知的明确续发/引用证据。单凭“老师”昵称、同学猜测、“是不是取消了”或无出处的转述不自动改变正式状态。可信发布者关系限定在对应群/课程内，不因一个群的确认而在所有群自动获得同样权限；新证据不足时提供候选供用户核对。

规则记录分别说明行动、相关性、时间、来源和关联的判定依据，不把单一总分当作所有条件可靠的保证。用户纠正误分类、错误时间或合并关系后，记录该次修正；同一消息重跑不会撤销修正或重新制造已拒绝候选。

### 7.2 拆分、跨群合并与纠错

- 一条消息包含不同交付物、不同需要完成的行动或分别适用的时间时，创建独立事项并共享证据；例如“明天交实验报告，下周交课程论文”生成两项任务。对同一交付物的格式要求保留为同一任务内容，不机械地每句话建一项。
- 报名截止和活动开始作为关联事项保存，按第 2.1 节决定任务/通知及提醒。引用同一消息的各项任务独立完成，完成其中一项不修改其他项。
- 群内重复接收与历史重叠按账号、群、消息 ID 去重；跨群广播属于事项层合并，要求有明确同一原通知/引用关系，或已确认课程、对象、行动和时间一致的充分证据。仅标题、关键词或文字相似不足以自动合并；不同班级或不同作业轮次不能合并。
- 自动合并保留全部来源、原消息及变更记录。正式时间、手动覆盖或完成状态存在冲突时，生成待确认的合并建议并展示差异，不自动选较早截止或把已完成状态传播给另一项。
- 用户确认合并时选择保留事项及冲突字段/状态，旧事项 ID 保存跳转关系；保留历史台账，刷新卡片及旧 ID 跳转关系，详情定位当前事项。
- 用户拆开错误合并时逐项核对行动、时间、证据和状态；缺少可靠信息的拆出项进入待确认。拆分操作保留来源和历史台账，新 ID 不触发系统通知；按拆分后状态刷新卡片，旧合并 ID 定位相关事项列表。
- 合并、拆分和用户“保持独立”的决定保存在本地，重复读取同一证据不再次自动合并。新实质证据引发冲突时提出新建议，不覆盖已有纠错决定。

### 7.2.1 课程关联修正后的历史修复

- 用户保存课程/群关联修改后，按新关联版本重新检查受影响群仍保留的本地消息和已有事项证据，记录实际检查范围、数量及结果；优先覆盖保留的最近 7 天消息，不承诺恢复已清理的未关联消息。
- 重查以原消息及既有事项 ID 去重，沿用原发送时间和有效变更顺序，保留手动字段、人工确认/拒绝/忽略、合并拆分决定、已完成/已取消/已归档状态和已发送提醒记录；不把重查当成新的实时发布。
- 原来被自动判为无关但现在可靠相关的消息可以提取；不确定的进入待确认。已有事项的自动课程归属可按可靠新关联修正；与手动字段冲突或原任务变得不相关时提出关联修正建议，不自动删除、完成、取消或归档旧任务。
- 修复结果逐步刷新列表和卡片，界面显示完成/部分失败及实际范围，失败可重试；旧消息重查不发系统通知，重复运行不生成同一任务。

### 7.3 手动字段、后续变更和撤销顺序

| 情况 | 正式状态与提醒处理 |
| --- | --- |
| 同一消息重放或普通重复证据 | 补齐证据，不回退手动字段，不重开已完成/已忽略事项，不重复提醒 |
| 明确有效变更涉及未手动覆盖字段 | 自动更新该字段并记录证据；影响时间时按新正式信息刷新卡片排序和高亮 |
| 新时间/课程等与用户已确认字段冲突 | 保存待确认差异，维持旧正式值及当前有效提醒，接受后再事务性替换；界面同时提醒“有未确认变更” |
| 已完成任务收到可靠新行动要求 | 关联与必要时间均有效时恢复待办，保留原完成记录并产生一次重要变更；其他情况形成关联待确认建议 |
| 可靠通知明确取消任务 | 更新为已取消，移出待办和卡片，保留取消证据；即使之前完成，也不能把取消当成再次完成 |
| 用户手动归档或从归档记录恢复 | 归档移出待办和卡片，保留证据；恢复采用最新有效信息刷新卡片 |
| 已归档任务收到可靠新行动要求 | 保存关联待确认建议，不自动覆盖归档状态；用户接受后才恢复待办 |
| 撤销完成，期间只有已接受的延期或补充 | 仅恢复待办状态，采用最新正式字段，保留新的证据；刷新卡片排序和高亮 |
| 撤销完成，但期间已明确取消或已因新要求恢复 | 旧撤销不再适用，显示替代原因，保留最新有效状态；不再次恢复或通知 |
| 撤销忽略，但期间已有确认、合并、拆分或后续有效处理 | 检查操作影响范围；已被替代时提示原因并保持当前结果，禁止恢复整个旧快照 |

变更和用户操作以后台事务顺序及依赖版本检查为准；两视图同时编辑、卡片查看后立即完成、取消与卡片操作同时到达时，都先读取当前正式状态再提交。取消不因一项手动时间覆盖而继续发旧截止提醒；未经确认的取消候选也不能停掉原提醒。

手动保护针对实际由用户填写、纠正或确认图片建议的正式字段；确认课程与群的关联不等于把该群所有任务字段都设为手动覆盖。可信老师的新延期与手动截止冲突时，保留旧正式值及当前提醒、展示差异并等待接受；用户接受后才替换及重算。未手动覆盖的可靠变更仍自动更新。明确取消继续按取消规则执行，不受手动时间保护阻挡。

### 7.4 本地规则的真实验收标准

- 建立可重复检查的真实群消息样本，覆盖短作业、多任务、相对日期、考试/报名、对象限定、疑问与否定、转述、跨群重复、催交、延期、取消、已完成后的新要求及 OCR 建议。规则调试样本和独立验收样本分开，同一通知的跨群副本放在同一集合，避免泄漏。
- 初始验收目标：自动建立正式任务的准确率至少 95%；需要本人行动的事项召回率至少 95%，召回包含正确进入待确认的候选；对已经自动接受的时间、取消、覆盖和恢复操作，独立验收样本中不得出现错误日期/时刻或错误目标操作。报告必须同时列出样本量、每类数量和错误例子，少量样本的零错误不代表普遍保证。
- 单独报告直接自动提取的覆盖率、待确认占比、按群统计的误报/漏报，以及至少一周正常使用中的每日待确认数量和处理时间；首次七天导入单列，不能用大量全部转待确认来宣称自动提取已通过。
- 未达到高影响变更的可靠性要求时，保留提取和待确认处理，将有问题的自动规则降为待确认，不通过降低时间或来源约束掩盖问题。校正规则后重跑独立样本及对应回归场景，不回写真实用户状态作实验。
- 本节是真实样本的开发验收目标。M2 已运行消息标准化、日期解析、行动识别、优先级和合成样本回归，结果见 [本地规则基线](../../verification/rule-baseline.md)；尚未运行真实独立群消息验收。规则不保证理解任意自然语言；复杂省略、同一动词多个交付物和跨句指代仍需真实样本增强，不能承诺全部自动识别或全部转为待确认。

## 8. RapidOCR 和图片证据

2026-10-28 用户已授权图片下载、本地 OCR 和原图备份接入，按[图片实施计划](../plans/2026-10-28-image-ocr.md)执行；替代此前 OCR 后置安排。图片日期仍须用户确认，原消息和人工结果保留；代码、合成验证、真实图片验收与发布状态分别记录。

- 采用独立常驻工作进程和 CPU 模型，任务顺序处理；UI 不等待 OCR 阻塞。
- 模型、字典、推理运行库和 Python 解释器随安装包准备，用户无需另装系统 Python。
- 使用一行一个 JSON 的标准输入/输出通信，含请求标识、本地图片路径和结果；日志写到独立错误输出。
- 由 WPF 隐藏启动并重定向流；工作进程打包需保留标准输入/输出，不能使用会移除这些流的窗口模式。
- 图片保存为消息证据，返回文字、位置与置信度；正式日期字段只由有效文字或用户确认建立。
- 原文字时间完整时，OCR 结果仅作辅助；原文字缺少关键信息时提供建议并进入待确认。
- 工作进程退出或单图超时做有限重试，失败状态落库，不无限循环；原图继续可查看。
- 发布前验证断网加载全部本地模型，以及真实学校截图、长图、模糊日期和识别失败场景。

## 9. WebView2 消息桥和界面状态

- 本地 UI 资源映射到固定的虚拟 HTTPS 主机；主界面加载本地页面，桌面两卡片使用专用 WPF 视图。
- 页面通过 postMessage 发送带请求标识、操作类型和参数的 JSON，WPF 校验来源与参数，执行保存后返回结果。
- 仅提供加载、编辑、完成、归档、恢复归档、撤销、确认、忽略、通知转任务、合并、拆分、课程关联修改/重查及设置等明确操作；不开放任意命令或文件读写。备份、恢复和账号切换通过专用后端操作处理，文件选择由 WPF 提供，前端不能提交任意路径作为读写命令。
- 后端推送状态变化，主界面和桌面组件使用同一份正式数据，操作任何入口后其他视图同步更新。
- 主题、未读数量、完成状态、桌面布局和连接状态由后端统一管理。
- 群消息与 OCR 内容按文本展示，不作为 HTML 执行；图片只加载已保存的本地证据。
- 详情编辑保存失败时不丢弃表单；重复点击请求具有操作标识，避免重复完成或新增。
- 前端提交事项依赖版本；后台收到新证据、另一视图编辑或取消后，返回冲突及当前差异，保留用户输入供重新核对。查看详情仅确认实际显示的重要变更版本，不把加载期间新到达而未展示的变更标为已读。
- 待确认原因和可选处理动作由后端判定；前端不能把“接受建议”绕过缺失字段校验变成直接覆盖。合并、拆分成功后刷新两视图并更新旧 ID 定位关系。
- 前端组件复用现有原型视觉，但示例数据、重置示例及浏览器桌面模拟不作为真实应用功能发布。

## 10. Windows 桌面、托盘和自启动

### 10.1 桌面组件

- 以两张独立 WPF 窗口显示左右两张卡片，自动刷新 AccountWorkspace 当前账号快照，提供详情/完成及待确认入口；窗口不抢焦点，不出现在任务栏，不使用始终置顶（Topmost）。本轮实际附着 `SHELLDLL_DefView`，child/noActivate=true、topmost=false 已检查。
- 复用本机已验证的 Explorer 桌面宿主附着方式；这是 Explorer 内部行为，恢复及多屏仍须实际验收。
- 跨进程 SetParent 的 DPI/边界处理复用 DesktopGeometry；`desktop-layout.json` schema 1 原子保存 DIP 坐标和尺寸，读取时按当前缩放与边界约束，损坏/未知格式保留原文件。
- 验证 Win+D、普通窗口切换、鼠标操作、多显示器缩放、Explorer 重启和睡眠恢复；保存布局并在显示器变化后把组件移回可见区域。
- 附着异常时保留主界面与托盘处理入口，提示组件异常并尝试恢复。桌面显示行为未达到要求前，不能认为桌面卡片已完成或以置顶窗替代验收。

### 10.2 托盘、自启动和退出

- WPF 管理托盘入口及显示主界面、退出动作，窗口关闭按已保存设置处理。
- 安装到当前用户固定目录，用当前用户启动项实现登录后后台启动；设置开关与实际启动项保持一致。
- 后台启动后独立检测 NapCat 与 QQ，按第 6.1 节等待就绪；不把本应用的启动项开关解释为 NapCat/QQ 自动启动开关。
- 重复启动通过单实例协调；真正退出时停止接收与工作区刷新，保存布局，关闭 OCR 工作进程。
- 系统注销或关机时正常释放资源；下次启动继续未完成的处理，不因重启本身恢复已完成或已忽略的事项。收到明确新行动要求或用户有效撤销时，按对应规则恢复状态。

### 10.3 当前提示渠道边界

全部 Windows 系统通知和声音已取消，不接入 AppNotificationManager 自动投递、系统时间节点、批次汇总、断线提示、通知激活或权限恢复。普通 App 通知列表继续表示群消息中的普通通知；已有旧提醒库和通知探针留作历史，不删除数据。正式卡片首段的当前状态刷新与合成检查不代表完整真实任务验收。

卡片操作通过 AccountWorkspace 核对账号、事项 ID 和依赖版本；状态变化读取当前快照，完成/取消/归档移出卡片，延期及新要求刷新排序和标记。卡片详情在主界面查询当前正式状态及合并/拆分关系。
